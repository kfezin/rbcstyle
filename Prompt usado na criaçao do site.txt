## 9. Acessibilidade
- Texto alternativo (ALT) descritivo em todas as imagens de conteúdo e `alt=""` nas decorativas.
- Contraste adequado (WCAG AA no mínimo, 4,5:1 em textos), inclusive sobre fotos.
- Navegação completa por teclado: ordem lógica de foco, `:focus-visible` bem visível, "pular para o conteúdo", galeria e menus operáveis por teclado.
- ARIA só quando necessário; botões e links com nomes claros; alvos de toque com tamanho adequado.
- Lenis e animações não podem atrapalhar teclado, leitores de tela ou o zoom. **[ADICIONADO]**

## 10. Configurável e escalável
- Todo o conteúdo editável em arquivos de dados (`src/data/site.js`, `src/data/servicos.js`, `src/data/galeria.js`): contato, textos, estilos, preços, regras, pagamento, links.
- Para adicionar um estilo ou foto, basta editar o arquivo de dados, sem mexer na lógica.
- Componentes e módulos pequenos e reutilizáveis (`src/modules/…`); CSS organizado por camadas (variáveis, base, componentes, seções).
- Sem duplicação, funções gigantes ou código monolítico. Nomenclatura consistente.

## 11. Publicação sem erros de caminho
- `vite.config.js` com `base: './'`.
- Nenhum caminho absoluto começando com `/` para assets, imagens, fontes, CSS ou JS. Usar caminhos relativos ou imports do Vite (`new URL('./img/x.png', import.meta.url)`).
- O `npm run build` + `npm run preview` precisam funcionar, e o site tem que funcionar também em subpasta.
- Pronto para hospedagem estática (Netlify, Vercel, GitHub Pages, hospedagem comum). Incluir instruções de deploy.
- Links externos com `rel="noopener noreferrer"`.

## 12. Segurança e boas práticas de código
- Código limpo, organizado, indentado e legível, sem linhas excessivamente longas, funções gigantes, código monolítico, duplicações ou complexidade desnecessária. Padrões de nomenclatura, modularização e arquitetura.
- Nunca expor credenciais. Sem inline scripts; incluir Content-Security-Policy e demais cabeçalhos de segurança (arquivo `_headers` ou meta, conforme o host). **[ADICIONADO]**
- Proteção contra XSS (não usar `innerHTML` com dados externos). Como a página é estática e sem formulário, SQL Injection, CSRF, autenticação, banco de dados e validação no servidor não se aplicam agora. Se o projeto ganhar backend, siga: validar dados no servidor, consultas parametrizadas, autenticação e autorização, permissões, proteção de dados sensíveis, tratamento de erros sem expor informações internas, transações e integridade do banco.
